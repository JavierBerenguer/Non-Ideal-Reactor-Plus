Appendix

Units, RTD, ReactionSys, and Stream

This appendix explains the common objects that move across tabs and the internal SI convention that keeps the numerical core consistent. If later tabs seem to disagree with what you thought you loaded, the issue is often in object state or unit interpretation rather than in the solver itself.

Internal SI Convention

The app works internally in the International System of Units (SI). Unit dropdowns exist to make input and display convenient, but the core models stay in SI internally.

Why this matters: a value that looks small or large in the UI can still be perfectly correct internally if it has been converted to or from SI. Many apparent inconsistencies are really unit-translation misunderstandings.

How Shared Objects Flow Across Tabs

The tabs do not all duplicate each other. Some inherit objects directly, some cache results, and some expect an earlier tab to have already built the required state.

RTD

The RTD object stores the residence time distribution, its moments, and metadata associated with its origin or family. It is generated first because later calculations depend on it.

  • Tab 1 builds it directly.
  • Tab 2 consumes it as the real hydrodynamic input for Segregation and Maximum Mixedness.
  • Tabs 3 and 4 can derive equivalent hydrodynamic models from it.
  • Tab 5 uses either the Tab 1 RTD or a fitted RTD derived inside Diagnosis & Fit.

ReactionSys

The ReactionSys object stores stoichiometry and kinetics. The app assumes that the entered rate expressions are consistent with the stoichiometric matrix.

Important: when the user writes custom kinetics, the app expects reaction-rate expressions that are consistent with the stoichiometric definition. A visually plausible formula can still be wrong if it is tied to the wrong species-balance convention.
  • Species order matters because rate expressions and stoichiometric rows are index-based.
  • Selectors across the app fall back to names such as CA, CB, CC if explicit component names are unavailable.
  • Some routes, such as Dispersion Model with open-open, impose additional kinetic restrictions.

Stream

The Stream object stores the inlet state used by the reactive routes. In the current Tab 5 Optimization workflow, inlet concentrations are the active manipulated variables.

Because the app keeps internal SI consistency, changing the display units of a stream does not change the internal values used by the models.

  • The stream defines the inlet composition and flow state later converted into C0 and related model inputs.
  • Optimization inherits its input concentration units from the loaded stream instead of creating a separate unit system.
  • If later tabs display unexpected concentration magnitudes, verify the stream definition before suspecting the reactor model.

Where Display Units Change and Where They Do Not

Layer What changes
Input widgetsUser-facing values are converted from the chosen unit into internal SI.
Core solversValues stay in internal SI for consistency.
Result tables and plotsValues are converted back into the currently selected display units.

This is why changing a display unit should change presentation, not the underlying physics.

Common Cross-Tab Mistakes

Symptom Usually check first
A later tab says an object is missingWhether it was actually generated or loaded in the current session, not just configured partially.
Values look off by a factor of 1000Concentration or volume unit interpretation.
Species names look genericWhether explicit component names were defined; otherwise the fallback naming is expected.
Optimization bounds seem strangeRemember that displayed bounds follow the inherited input unit, while the solver still works in SI.
