Appendix

How Objects, Computations, and Sessions Move Across Tabs

This appendix explains the practical workflow behavior that is easy to miss when using the app for the first time: which objects are foundational, what later tabs inherit, what later tabs recompute, and why a saved session can restore state without automatically repainting every derived result block.

Core rule: later tabs are usually not fixing missing foundations. They assume these objects already exist in a coherent form.

When You Still Need Compute

Restoring or selecting an object is not always the same as rebuilding every display artifact derived from that object. Some tabs store enough state to repaint more directly; others still need a fresh computation to regenerate their displayed summaries, plots, or comparison tables.

  • If a view looks configured but still blank, try Compute before assuming the session is broken.
  • If a tab offers a "From Calculated Data" route, confirm that the upstream calculation really exists and matches the intended session state.
  • If you changed units or a selector, ask whether that action only re-expresses results or whether it requires a new numerical solve.
Simple practical habit: think in two layers: state restoration first, result regeneration second.

What Restored Sessions Really Restore

  • They restore the saved configuration and the app state that was serialized at save time.
  • They do not guarantee that every computed visual block will be freshly rebuilt unless the current tab logic does that automatically.
  • They are best understood as restoring context, not as magically re-solving every model route on load.
If you observe... First interpretation
The correct RTD source is visible but a downstream plot is emptyThe view may need a fresh Compute.
The right chemistry names appear but tables remain staleThe objects are present, but the active tab may not have rebuilt its result cache yet.
An equivalent-model tab looks inconsistent with Tab 1Check whether it is reusing imported data, a local parameter mode, or an older computed context.

Typical Workflow Mistakes

  • Expecting every tab to be self-sufficient even when the current design is intentionally upstream-dependent.
  • Confusing "the controls show the right names" with "the current view has already recomputed the derived results".
  • Jumping into Optimization before verifying the RTD and chemistry together in Prediction Models or Reactive Performance.
  • Using "From Calculated Data" without confirming that the upstream source really belongs to the current session state.
